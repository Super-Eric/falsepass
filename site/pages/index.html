How it works

A grader is an assertion. falsepass tests it the way you'd test any assertion you didn't write: feed it inputs whose right verdict you already know.

01

Point it at an environment

A Hub environment, a local folder, an Inspect AI task or a HUD environment. It is installed in its own throw-away virtualenv, pinned to the versions it was built for.

falsepass init owner/environment
02

Probe the grader

The reference answer and harmless variations of it; empty, echoed, every-option, hedged and wrong answers; malformed output; repeats. A mutation search and a static scan of the reward source join in.

falsepass audit environment --search 120
03

Confirm, then fix

Every failing probe becomes a stand-alone repro that needs only the environment's own packages. Patch the grader and rerun it to see exactly which rows change.

falsepass repro environment --probe P5

What it keeps finding

Run on a few dozen public RL environments, the same handful of grader defects turned up again and again, across different authors.

Graders that count words

Free-form tasks scored by keywords. One generic text, sent for every task, beat the dataset's own reference answers.

return df # dropna fillna astype …

Rewards for the form

Format and reasoning terms that never look at the answer pay a wrong answer about a third of the maximum.

<think>…</think> \boxed{B} (wrong)

Strict and lenient in the wrong places

A trailing period scores zero; a denial with no answer marker at all scores full marks.

The answer is definitely not 42.

Denials inside the answer box

Normalisation built for units drops the text after a number, and only one side of an equation is compared.

\boxed{13 = 12}

Exceptions nobody sees

A reward term that raises on every call is caught, logged and recorded as zero. Runs finish with plausible numbers.

NameError: name 're' is not defined

Episodes that don't end

A game keeps answering after it's over, and the reward re-reads every message, so whoever keeps talking scores highest.

That was a great game!

Check every push

The GitHub Action fails the build when a known-bad answer earns reward, and puts the probe table in the job summary.

# .github/workflows/falsepass.yml
on: [push, pull_request]
jobs:
  falsepass:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: Super-Eric/falsepass@main
        with:
          path: .
          fail-on: "ceiling>0.1 errors>0"

An illustrative session. Any MCP client works the same way: setup for other clients →

Leads, not verdicts. A failing probe is a reason to read the reward code. A finding needs a repro that runs twice with identical output, the line that causes it, and a check of how many real tasks it affects. Strictness the prompt asks for, and graders that are exploitable on purpose, aren't bugs.

Used on a few dozen public environments. Fixes go to the maintainers first, as small pull requests.
